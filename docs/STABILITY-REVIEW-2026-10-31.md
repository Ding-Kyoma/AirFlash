# 稳定性审查：2026-10-31

审查基线为已发布的 v0.5.4（9711508），审查对象为 9f88e6a 及其相对发布版的大批改动。参考 docs/improvement_plan 的分析结果，但以本项目实际协议实现、配置兼容性和可验证的行为为准。此次生成开发构建，不对外发布，也不占用发布版本号。

## 结论与取舍

遥测、控制通道与媒体通道分离、localhost 协议模拟和显式接收器时钟跟随值得保留。商业软件的策略不能直接证明本项目的实现正确；尤其不能用本地 UDP 写入成功证明接收器仍归本发送端所有，也不能在没有接收器时钟更新协议的情况下移动 buffered 音频时间轴。

按用户确认的策略：保留旧组合；已知不兼容时显示提示，由用户手动拆分；确认其他控制器接管后停止发送、恢复本机声音，等待手动重连。取消未经验证的自动争回和启动前自动 BMCA 角色切换。显式时钟跟随仍保留。

## 已修复的问题

| 优先级 | 问题及影响 | 修复 |
| --- | --- | --- |
| P1 | 每包发送路径同步等待状态探测、TCP liveness 和事件通道重建，辅助通道故障能造成音频停顿。 | 改为有界后台任务；发送线程只取已完成结果；停止时取消并回收任务。移除生产路径的网关归因探测。 |
| P1 | 接收器主动 TEARDOWN 后，本地 UDP 写入成功仍覆盖接管证据；旧策略还可能自动争回。 | 保留当前会话已结束的证据，确认忙于其他控制器后产生不可重试的 preempted；不发送旧会话 TEARDOWN。普通断网仍按配置处理重试。 |
| P1 | buffered 音频无法发布新的时间锚，仍尝试原地重锚会使发送端和接收器时间轴不一致。 | 根据实际数据传输类型禁用动态位移；过期返回可重试 timeline_expired，沿现有流程重建会话。 |
| P1 | PTP 冻结路径依赖 Delay 时间，无法可靠保留 Sync-only 模式最后实际使用的映射。 | 缓存同一时钟关联最后已发布的映射；冻结有期限；更换关联时清空。 |
| P1 | 能力查询丢失型号、固件及组合拓扑，可能在真正连接前错误拒绝 Apple TV 或组合。 | 查询与播放共用完整指纹和组合时钟计划；缺失或非法固件保持未知；明确 PTP 允许未知证据，自动单设备策略保持保守。 |
| P1 | 旧配置升级会自动拆除混合组合，丢失组合选择、偏移和选项。 | 升级只更新版本标记；保留原组合和备份机制；已有运行时兼容性提示和手动拆分保留。 |
| P1 | 应用采集会扩展到多个同路径进程，可能采集用户没有选择的独立实例。 | 优先保持精确 PID 和启动时间；原实例退出后只跟随唯一候选，歧义时等待选择；保留 PID 复用防护。 |
| P1 | 为 SMTC 提升编译目标时同时抬高最低 Windows 版本，偏离已发布版支持范围。 | 保留 WinRT 编译投影，最低系统版本恢复为 Windows 10 1809 / 17763。 |
| P2 | 自适应延迟将总目标当作额外位移，使用累计 p99，状态跨重连残留，并提前报告未确认的调整。 | 用协商后的 codec/timing 计算基线；只发送额外位移；使用区间 p99、确认反馈和冷却期；尊重设备覆盖选项；新时间轴重置；buffered 不动态调整。 |
| P2 | 连续移动的播放位置使元数据永远无法通过稳定窗口；进度错误使用毫秒而非 RTP 时钟。 | 曲目信息稳定性与位置变化分开；初次连接补发缓存元数据；进度使用对应采样率的 32 位环绕 RTP 样本时间。 |
| P2 | 一个接收器的元数据成功会掩盖另一成员失败；失败请求可能持续争用共享 RTSP 控制连接。 | 按成员、按载荷记录发送状态；失败后降级该载荷，不无限重试。 |
| P2 | SendInput 的 INPUT 联合体尺寸错误；显式播放、暂停和随机/重复命令被错误映射为切换或下一曲。 | 修正原生布局；明确 play/pause 通过 SMTC，toggle 才使用媒体切换键；不把随机/重复映射为下一曲。 |
| P2 | 诊断导出启动新引擎，得到空会话；原始日志还可能包含地址和路径。 | 通过正在播放引擎的单一事件读取循环获取脱敏快照；空闲不启动新引擎；不附加原始日志；加强消息和 socket 地址脱敏。 |
| P2 | 重传请求消息数和请求包数混用，采集欠载被判成网络故障，排空是否受限由末次计数变化猜测。 | 统一包数单位；采集欠载仅标记发送端饥饿；使用实际排队长度及丢弃数，启动短窗口只采纳极端重传证据。 |
| P2 | 事件通道重建可能清除独立反馈故障，或覆盖刚重建连接的新故障。 | 按通道保存故障；在新事件读取线程开始前清除旧事件故障，保留后续故障及其他通道状态。 |
| P2 | QoS 注册发生在未连接 UDP socket 上，且未提供目的地址，可能始终失败。 | 在连接后注册，使用非自适应 flow；失败仍为可选功能降级。 |
| P2 | 非法或过期的 lead / metadata IPC 可能终止音频或污染新会话。 | 校验活动会话、类型和范围，返回非致命反馈；新 start 清空旧控制状态。 |

## 验证范围

提交前结果：.NET 582 项通过；Python 141 项通过；Ruff 通过；Rust 312 项通过、2 项按原定义忽略（真实采集设备和 30 分钟 soak）；Clippy 及 native release 构建通过。测试包含 localhost TCP/UDP 模拟。native 静态 CRT 和 Windows API 审计退出成功，其中 156 个导入仍标记为未确认，不能据此声称已在 Windows 10 运行验证。WPF 模拟 UI Smoke 及本地 main 开发构建结果以本次任务最终说明为准，详细日志保存在未提交的 artifacts 目录。

没有执行真实 HomePod 播放、Windows 10 旧系统虚拟机、MSI 安装/升级/卸载验证。开发构建成功不能替代这些验证。QoS 是否被实际网络设备采纳、低延迟阈值是否适用于所有固件均未得到硬件验证；现有延迟阶梯应视为可选策略，不能视为接收器实际缓存容量。空闲诊断只可能复用此前取得的快照，不会伪造已结束会话的数据。

一次高并发 Rust 运行触发了原有的 80 ms 待机测试调度竞争：测试生产者在进入待机后又写入音频，导致“仍无新音频”的断言失败。没有放宽断言；后续完整 Rust 检查使用 4 个测试线程，以减少本机并发负载影响。
